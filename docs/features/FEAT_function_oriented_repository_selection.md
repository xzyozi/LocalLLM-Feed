# [FEAT] 関数提供型・モジュール型リポジトリ優先選定

- **文書番号**: SRF-FEAT-003
- **作成日**: 2026-08-31
- **ステータス**: 設計・検討中 (Proposed)
- **対象**: `collector.py`, `extractor.py`, `scorer.py`, `models.py`, `pipeline.py`

## 1. 背景・目的

ScholarRepo-Finder は、研究・検証用途で再利用できる実装を見つけることを目的とする。現行の依存ライブラリ数中心の評価では、ML系を含む複数依存プロジェクトが有利になり、公開APIやモジュール分割を備える軽量な実装を十分に評価できない。

本機能では、関数・クラス・モジュール・ライブラリを提供する候補を優先し、実行専用アプリケーションより上位に選定する。MLであることは優先条件にも除外条件にも使用しない。

## 2. 用語と対象

用語は [SRF-CX-001 用語集](../design/SRF-CX-001_用語集.md) を正とする。

1. **関数提供型リポジトリ**: 他プログラムから呼び出せるAPIまたはライブラリを提供する。
2. **モジュール型アプリケーション**: 実行入口を持つが、ロジックが責務別モジュールに分離されている。
3. **実行専用アプリケーション**: 再利用可能な境界を確認できない実行主体のリポジトリ。

Cの公開ヘッダと実装ファイルの組、Pythonのimport可能なパッケージ、Rustの`lib.rs`、JavaScript/TypeScriptの公開exportを、関数提供型を示す代表的な根拠として扱う。

## 3. 機能要件

1. 候補ごとに、`library`、`modular_application`、`executable_application`、`unknown` のいずれかの提供形態を推定・保存する。
2. 公開API、モジュール分割、利用方法の説明、設定可能な入出力を再利用性の根拠として抽出する。
3. MLライブラリ、Papers with Code、科学計算ライブラリの存在は、検索・表示用属性として保持しても、直接加点には用いない。
4. 配点、評価軸の上限、ハードフィルター、掲載閾値、信頼度乗数は `config/scoring.toml` から読み込む。設定ファイルは唯一の設定源とし、Python 3.11以降の標準ライブラリ `tomllib` でコメント付きTOMLを解析する。コードに配点を重複定義しない。
5. 初期プロファイル `reusability-v1` は、再利用性30点、保守性20点、研究文脈50点を基礎スコアとし、提供形態・公開API・モジュール分割・利用手順・設定可能I/Oを再利用性の根拠とする。
6. 設定検証に失敗した場合は評価を開始せず、暗黙の既定値フォールバックを行わない。
7. 最終選定時には、提供形態別・シードカテゴリ別の候補数、通過率、スコア内訳、適用設定のID・版・ハッシュを記録する。
8. 言語に依存しない共通基準を使用し、言語固有の検出器は根拠抽出のためにのみ使う。

## 4. 受け入れ基準

- Cの`.h`と責務別`.c`を持つ候補が、`src/`配下でないことだけを理由に不利にならない。
- Python・Rust・JavaScript/TypeScriptの公開APIを持つ候補を、同等の再利用性として評価できる。
- ML系依存の有無だけでは、同じ再利用性を持つ候補間で点差が生じない。
- 提供形態・スコア内訳・選定結果を集計し、分野偏りを継続的に確認できる。
- `config/scoring.toml` の配点だけを変更した場合、評価器のコードを変更せずに結果を再計算できる。
- 不正な設定は評価開始前に明示的なエラーとして報告され、部分的な配信データを生成しない。
- 同一入力と同一設定では、設定ID・版・ハッシュを含む同一の観測結果を生成できる。

## 5. 実装前の注意

特徴抽出・提供形態の観測、設定駆動の評価・選定・配信データ出力は実装済みである。配点を変更する際は、`config/scoring.toml` のコメントに判断理由を残し、同一入力で公開JSONと観測レポートを再生成して差分を確認する。
